# 次に進める作業

## 前提

- 要件定義は `Docs/Requirements` 配下を正とする。
- 現状の実装は、マスターデータ定義、周回内セーブデータ、ショップ、合成、ホーム/ショップ/合成系UIが先行している。
- 次の大きな未実装領域は、条件判定、イベント実行、クエスト進行、戦闘実行、タイトル/セーブ画面である。
- Prefab は明示指示があるまで触らない方針のため、まずはロジックとテストを優先する。

## 優先順位

### 1. 条件判定サービス

`ConditionGroup` / `Condition` を `RunSaveData` に対して評価する共通サービスを作る。

理由:

- イベント発生条件、クエスト解放条件、うろつき場所解放条件、選択肢表示、クエストノード接続条件で共通利用する。
- ここがないとイベント・クエスト・うろつきの実行系を安全に進めにくい。

作業内容:

- `ConditionEvaluator` を追加する。
- `all` / `any` を評価する。
- `flag`, `day`, `phase`, `mainProgress`, `questState`, `questCleared`, `questFailed`, `characterJoined`, `characterInParty`, `characterEventStage`, `itemCount`, `equipmentOwned`, `eventOccurred` を実装する。
- 要件にある `synthesisLevel` 条件がコード上の `ConditionType` にないため追加する。
- `battleResult` は戦闘結果保存仕様がまだ薄いため、最初は未対応扱いまたは明示的に false とする。

完了条件:

- EditMode テストで主要条件と比較演算が通る。
- 空条件は成立として扱える。
- 未知/未対応条件の扱いがテストで明確になっている。

### 2. イベント効果適用サービス

`EventEffect` を `RunSaveData` に反映する共通サービスを作る。

理由:

- 仲間加入、クエスト解放、うろつき場所解放、報酬付与、フラグ更新、戦闘開始など、要件の進行変更はイベント効果に集約されている。
- クエスト成功報酬もイベント効果で処理する方針なので、クエスト実行前に必要。

作業内容:

- `EventEffectApplier` を追加する。
- `SetFlag`, `SetVariable`, `AddVariable`, `JoinCharacter`, `LeaveCharacter`, `UnlockQuest`, `UnlockWanderLocation`, `AddItem`, `RemoveItem`, `AddMoney`, `RemoveMoney`, `AddEquipment`, `UnlockEpilogue` の扱いを決めて実装する。
- `StartBattle` は直接戦闘を開始せず、呼び出し側へ開始要求を返す形にする。
- 要件にある合成レベル変更が `EventEffectType` にないため、必要なら `SetSynthesisLevel` / `AddSynthesisLevel` を追加する。

完了条件:

- 効果ごとの保存データ変更が EditMode テストで確認できる。
- 失敗しうる効果は保存データを中途半端に壊さない。

### 3. イベント選択・実行の最小コア

イベント候補から発生イベントを選び、イベント完了時に効果を反映するロジックを作る。

理由:

- 1日目、11日目、21日目、31日目、41日目の節目イベントとうろつきイベントの基盤になる。
- 画面実装前に、イベント選択ルールをテストで固められる。

作業内容:

- `EventSelector` を追加する。
- 発生済みイベントを除外する。
- 優先カテゴリの順序を実装する。
- 強制イベントは1日1件、重要/通常/汎用は条件に応じて選ぶ。
- 重み抽選はランダム注入可能にしてテストしやすくする。
- `EventData.steps` の全文表示UIは後続とし、まずは完了時効果の反映までを扱う。

完了条件:

- 強制、重要、通常、汎用の選択順がテストで保証される。
- 発生済みイベントが再発生しない。
- fallbackEventId を持つうろつき場所に接続できる設計になっている。

### 4. クエスト進行サービス

`QuestData` のノードを進めるサービスを作る。

理由:

- クエストは日数消費、報酬、戦闘、イベント、エンディング条件の中心になる。
- 戦闘UIの前でも、ノード遷移・宝箱・終了判定は先に固められる。

作業内容:

- `QuestRunService` を追加する。
- 解放済みクエストだけ開始可能にする。
- 開始時に挑戦中状態と現在ノード状態を保存する。
- 接続条件を `ConditionEvaluator` で評価する。
- `treasure` ノードで `RewardEntry` を付与する。
- `end` ノード到達でクリア状態にし、クリアイベントIDを返す。
- 撤退/敗北時の retryPolicy 反映を実装する。

完了条件:

- repeatable / untilClear / once の状態遷移がテストで保証される。
- 宝箱報酬が即時取得される。
- クエスト終了後の日数進行は呼び出し側で実行できる形になっている。

### 5. 戦闘ロジックの最小実装

UIなしでターン制戦闘を進めるコアロジックを作る。

理由:

- 要件の中で最も範囲が広く、UIと同時に作ると検証が難しい。
- まずダメージ、行動順、逃走、勝敗、報酬をテスト可能にする。

作業内容:

- 戦闘参加者のランタイム状態を定義する。
- 通常攻撃、スキル効果、HP/SP、勝敗判定を実装する。
- 逃走成功率を要件式どおり実装する。
- 敵行動選択を priority / weighted で実装する。
- 敵ごとの経験値・お金・ドロップ集計を実装する。
- 状態異常/バフ/デバフは最小セットから段階的に追加する。

完了条件:

- ダメージ計算、逃走率、勝敗、報酬集計の EditMode テストがある。
- BattleData の `canEscape`, `escapeCountsAsClear`, `gameOverOnDefeat`, `defeatResultType` を結果に反映できる。

## 直近の推奨着手

最初に着手する作業は「条件判定サービス」とする。

理由:

- 既存のマスターデータ構造にすでに `ConditionGroup` があり、Prefab 変更なしで進められる。
- イベント、クエスト、うろつき、選択肢、ショップ/合成の将来条件にも横展開できる。
- 実装範囲が小さく、テストで完了判定しやすい。

最初の小タスク:

1. `ConditionType.SynthesisLevel` を追加する。
2. `ConditionEvaluator` を追加する。
3. `RunSaveData` に対する条件評価テストを追加する。
4. 空条件、all/any、日数、フェーズ、メイン進行度、フラグ、変数、アイテム数、装備所持、クエスト状態、仲間加入、パーティ、イベント発生済み、合成レベルをテストする。
