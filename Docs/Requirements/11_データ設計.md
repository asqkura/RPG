# データ設計

## 基本方針

マスターデータは Unity の ScriptableObject として管理する。
各マスターデータは、ScriptableObject 参照に加えて一意な文字列IDを持つ。

```text
文字列ID + ScriptableObject参照
```

この方式を、スキル、アイテム、装備、敵、クエスト、イベントなどの主要データで共通方針とする。

## 文字列IDを使う場面

文字列IDは、データそのものではなく、データを安定して識別するために使う。

- セーブデータ
- イベント条件
- イベント効果
- クエスト解放条件
- クエストノードの参照
- 報酬指定
- エンディング判定
- 周回引き継ぎ記録

例:

```text
skillId
itemId
equipmentId
enemyId
questId
eventId
characterId
battleId
```

## ScriptableObject参照を使う場面

ScriptableObject参照は、Unityエディタ上でデータ同士を安全に接続し、実行時に直接扱いやすくするために使う。

- UI表示
- 戦闘中のスキル実行
- アイテム効果処理
- 装備性能参照
- 敵編成
- ショップ商品
- 合成レシピ
- デバッグ確認

## マスターデータ管理

マスターデータは、個別ScriptableObjectと種別別Databaseアセットで管理する。

```text
個別ScriptableObject + 種別別Databaseアセット
```

### 個別ScriptableObject

各データは個別のScriptableObjectとして作成する。

- `SkillData`
- `ItemData`
- `EquipmentData`
- `EnemyData`
- `QuestData`
- `BattleData`
- `EventData`
- `CharacterData`
- `RecipeData`

個別ScriptableObjectは、各データの編集単位とする。
表示名、説明文、Sprite参照、ステータス、効果、条件などは個別データ側に持たせる。

### 種別別Databaseアセット

データ種別ごとにDatabaseアセットを作り、対象データの一覧を保持する。

- `SkillDatabase`
- `ItemDatabase`
- `EquipmentDatabase`
- `EnemyDatabase`
- `QuestDatabase`
- `BattleDatabase`
- `EventDatabase`
- `CharacterDatabase`
- `RecipeDatabase`

Databaseアセットは、主に以下の目的で使う。

- 文字列IDからScriptableObjectを検索する。
- 登録漏れを確認する。
- ID重複を検出する。
- デバッグ時にデータ一覧を確認する。
- 実行時に必要なマスターデータへアクセスする。

### 単一Databaseは初期要件では作らない

すべてのデータをまとめた巨大な単一Databaseは初期要件では作らない。
データ種別ごとに分け、編集範囲と責務を小さく保つ。

将来的に必要になった場合のみ、種別別Databaseを束ねる上位の `GameDatabase` を検討する。

## IDと参照の使い分け

- データ定義内では、必要に応じてScriptableObject参照を使ってよい。
- セーブデータにはScriptableObject参照を直接保存せず、文字列IDを保存する。
- イベントやクエストの条件・結果は、原則として文字列IDで記述する。
- 実行時には、文字列IDから対象のScriptableObjectを引けるようにする。

## IDのルール

- IDは一度使ったら安易に変更しない。
- 表示名を変えてもIDは変えない。
- IDはデータ種別ごとに一意にする。
- セーブデータやイベント条件で使用中のIDを削除する場合は、移行または代替処理を用意する。

## Sprite参照

アイコンや敵グラフィックは、ScriptableObject上でSprite参照として持つ。

- スキル: `iconSprite`
- アイテム: `iconSprite`
- 装備: `iconSprite`
- 敵: `enemySprite`

画像そのものを文字列IDだけで参照する方式にはしない。
Unityエディタ上でSpriteの未設定を確認できる形にする。

## 条件データ

イベント、クエスト解放、うろつき場所解放、選択肢、クエストノード接続、エンディング判定などは、共通の条件形式を使う。

### Condition

単一条件を表す。

```text
conditionType
targetId
operator
value
```

- `conditionType`
  - 条件種別。

- `targetId`
  - 判定対象ID。
  - フラグID、クエストID、キャラクターID、アイテムIDなど。
  - 日数やメイン進行度のように対象IDが不要な条件では空にしてよい。

- `operator`
  - 比較方法。
  - `==`
  - `!=`
  - `>=`
  - `<=`
  - `>`
  - `<`

- `value`
  - 比較値。

### ConditionGroup

複数条件をまとめる。

```text
matchType
conditions
```

- `matchType`
  - `all`
  - `any`

- `conditions`
  - 条件一覧。

`all` はすべての条件を満たした場合に成立する。
`any` はいずれかの条件を満たした場合に成立する。

初期要件では、ConditionGroupのネストは扱わない。
AND/ORは1階層の `all` / `any` で表現する。

### 条件種別

初期要件で使う条件種別:

- `flag`
- `day`
- `phase`
- `mainProgress`
- `questState`
- `questCleared`
- `questFailed`
- `characterJoined`
- `characterInParty`
- `characterEventStage`
- `itemCount`
- `equipmentOwned`
- `synthesisLevel`
- `battleResult`
- `eventOccurred`

### 条件例

```text
conditionType: flag
targetId: forest_route_open
operator: ==
value: true
```

```text
conditionType: day
targetId:
operator: >=
value: 11
```

```text
conditionType: itemCount
targetId: iron_ore
operator: >=
value: 3
```

## 報酬データ

宝箱、戦闘ドロップ、固定報酬などの報酬リストでは、共通の `RewardEntry` を使う。
イベントによる状態変更は `EventEffect` を使い、`RewardEntry` は報酬一覧を表す用途に絞る。

### RewardEntry

```text
rewardType
targetId
amount
dropRate
```

- `rewardType`
  - 報酬種別。
  - `money`
  - `item`
  - `equipment`
  - `exp`

- `targetId`
  - 報酬対象ID。
  - `item` なら `itemId`。
  - `equipment` なら `equipmentId`。
  - `money` や `exp` では空にしてよい。

- `amount`
  - 個数、金額、経験値量。

- `dropRate`
  - 入手率。
  - 戦闘ドロップでは確率として使う。
  - 宝箱や固定報酬では100%として扱う。

### 用途

- 宝箱ノードの報酬。
- 戦闘ドロップ。
- 固定の短い報酬リスト。

### RewardEntryに含めないもの

- キャラクター加入。
- クエスト解放。
- うろつき場所解放。
- フラグ更新。
- エピローグ候補解放。

これらは `EventEffect` で扱う。

## 周回内状態管理

周回内の状態は、用途ごとに以下へ分けて保存する。

```text
flags
variables
occurredEventIds
questStates
characterStates
```

### flags

true/false の状態を管理する。

例:

```text
forest_route_open = true
met_old_smith = true
```

主な用途:

- 一度だけの分岐。
- 選択肢の結果。
- ルート解放。
- イベント条件。

### variables

数値状態を管理する。

例:

```text
mainProgress = 2
char_a_event_stage = 1
smith_trust = 3
```

主な用途:

- メイン進行度。
- キャラクターイベント段階。
- NPC進行段階。
- 簡易的な数値カウンタ。

キャラクターイベント段階は専用構造を作らず、`variables` に入れる。
Condition と EventEffect から共通的に参照・更新できるようにする。

### occurredEventIds

周回内で発生済みのイベントIDを管理する。

- 同じイベントの再発生防止に使う。
- 周回終了時にリセットする。
- 永続保存しない。

### questStates

クエストごとの状態を管理する。

- 未解放
- 解放済み
- 挑戦中
- クリア済み
- 失敗済み

### characterStates

キャラクターごとの現在状態を管理する。

- 加入状態
- レベル
- 経験値
- 現在HP/SP
- 隊列
- 装備中の装備個体ID
